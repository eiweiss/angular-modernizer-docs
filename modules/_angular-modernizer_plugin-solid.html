    Module @angular-modernizer/plugin-solid - v1.2.0

    SOLID principles plugin for the Angular Modernizer.

    SolidPlugin registers seven analysis rules and two transform rules:

    • DIPViolationRule: Dependency Inversion
    • ServiceDipViolationRule: concrete service injection (deprecated, reports nothing)
    • SingleResponsibilityRule: Single Responsibility
    • OCPViolationRule, GodSwitchAnalysisRule: Open/Closed
    • LSPViolationRule: Liskov Substitution (deprecated, reports nothing)
    • ISPViolationRule: Interface Segregation
    • GodSwitchTransformRule: replaces a large switch with a factory and strategy classes (GodSwitchTransformOrchestrator)
    • ServiceDipViolationTransformRule: replaces concrete constructor injection with an interface and an InjectionToken (ServiceDipViolationTransformOrchestrator)

    @angular-modernizer/plugin-solid

    SOLID principle violation detection and architectural analysis for Angular codebases.

    Overview

    The @angular-modernizer/plugin-solid package provides analysis rules for detecting violations of SOLID principles and other architectural issues. This plugin powers the scan-solid tool in the MCP server.

    SOLID Principles Coverage

    Single Responsibility Principle (SRP)

    Reports classes that are too large: more than 15 instance methods, Angular lifecycle hooks, accessors and function-valued properties not counted. Components and static-only classes are skipped. The rule makes no claim about responsibilities: it reads neither member names nor method bodies.

    Open/Closed Principle (OCP)

    Reports if-else chains that dispatch on one value in more than 4 conditions, and (solid:god-switch) switches with more than 10 clauses that do more than return or assign a value. Both grow with each new case.

    Liskov Substitution Principle (LSP)

    solid:lsp-violation is deprecated and reports nothing: a missing interface member or abstract method is a compile error, and an instanceof check alone shows no broken substitution. The id stays registered so configurations load; ConfigLoader warns when it is configured.

    Interface Segregation Principle (ISP)

    Reports interfaces that declare more than 5 methods (overloads once, function-typed properties included).

    Dependency Inversion Principle (DIP)

    Reports @Injectable classes of the project created with new and Injector.get() lookups inside class members: both bypass Angular DI. solid:service-dip-violation (concrete constructor injection) is deprecated and reports nothing; injections against the layer direction are imports that architecture:layer-boundary-violation reports.

    Analysis Rules

    SingleResponsibilityRule

    Rule ID: solid:srp-single-responsibility-violation Severity: Warning

    One finding per class (violationType: 'too-many-methods', at the class) when the class has more than 15 instance methods. Counted: method declarations that are not static (public, protected, private, # and abstract alike), an overloaded method once. Not counted: the Angular lifecycle hooks ngOnInit, ngOnDestroy, ngOnChanges, ngDoCheck, ngAfterViewInit, ngAfterViewChecked, ngAfterContentInit and ngAfterContentChecked (by exact name), get/set accessors and properties, also arrow-function and function-expression properties and signal fields such as input(), output(), model(), computed() and effect().

    Skipped: components (@Component and the decorators of parser.componentDecorators; architecture:component-complexity reports component size) and static-only classes. Directives, pipes, services and plain classes are counted.

    Message: Class 'UserService' has 16 instance methods without lifecycle hooks (threshold: 15). Metadata: className, methodCount, threshold, violationType, principle.

    Member names and method bodies are not read: the former checks for responsibility keywords in member names (mixed-responsibilities) and in method bodies (single-method-multi-concern) are removed. Responsibilities of services are reported by architecture:service-bag.

    DIPViolationRule

    Rule ID: solid:dip-violation-direct-instantiation Severity: Warning

    One warning per finding (result.severity). Violation types (violationType in the metadata):

    • direct-instantiation: new X() where X resolves by symbol to a class declared in the project (not in a .d.ts file or node_modules) with an Injectable decorator from @angular/core (named, aliased or namespace import). Library classes (new HttpClient(handler), third-party clients) and undecorated helpers or models are not reported, whatever their name. Metadata: instantiatedType (class name without qualifier or type arguments).
    • service-locator-pattern: .get(...) on a receiver whose type is Angular's Injector (type checker), any receiver expression: this.injector, a parameter, inject(Injector). A Map or other receiver only named like an injector is not reported. Metadata: receiver, token.

    Both are reported only inside class members (methods, constructors, accessors, property initializers). Not reported: a function that is the value of a useFactory property, a function passed to provideAppInitializer, provideEnvironmentInitializer or providePlatformInitializer, decorators and functions outside classes, since these build providers.

    suggestedFix proposes inject(X) when the project uses Angular 14 or later (api angularMajorVersion, installed @angular/core first, else the declared range) and the call site is an injection context (an instance field initializer or the constructor body, not a nested callback); otherwise a constructor parameter. Metadata also carries principle: 'DIP', injectionContext and angularMajorVersion.

    Reported:

    @Injectable({ providedIn: 'root' })
    export class UserService {}

    @Component({...})
    export class UserComponent {
      private userService = new UserService();             // direct-instantiation, fix: inject(UserService)

      constructor(private injector: Injector) {}

      load() {
        return this.injector.get(UserService);             // service-locator-pattern, fix: constructor parameter
      }
    }

    Not reported:

    export class ApiFactory {
      create(handler: HttpHandler) {
        return new HttpClient(handler);                    // library class
      }
    }

    export const PROVIDERS = [
      { provide: UserStore, useFactory: (injector: Injector) => injector.get(UserService), deps: [Injector] },
    ];

    ServiceDipViolationRule

    Rule ID: solid:service-dip-violation Status: Deprecated, reports nothing (removed in 2.0)

    Injecting a concrete @Injectable class is Angular's normal DI and no defect. The only harmful shape, an injection against the layer direction, is always an import upwards, which architecture:layer-boundary-violation reports for the configured layers / layersSource (and suppresses with its suppressionComments markers). The id stays registered so configurations load; ConfigLoader warns when rules['solid:service-dip-violation'] is set. The transform ServiceDipViolationTransformRule detects its targets itself and is not affected.

    GodSwitchAnalysisRule

    Rule ID: solid:god-switch Severity: Warning

    Reports a switch statement with more than 10 non-lookup clauses (threshold maxCases, default 10), one warning per switch at the switch. Switches are checked everywhere in the file.

    How clauses are counted:

    • A clause is a label with a body of its own: labels that fall through without statements form one clause with the next label that has statements. default counts like a case clause when it has a body.
    • A clause is a lookup when its body, ignoring break and unwrapping blocks, is a single return or a single assignment expression statement and contains no call or new expression (return 'x', return row.active ? row.on : row.off, this.label = 'x'), or whose value is one call with only constant arguments: literals, enum members and const variables (return translate.instant('HEADER.NAME')). return this.compute() and return handle(input) are no lookups. Lookups are not counted, so a value mapping is never reported. return this.compute() is no lookup.
    • A clause whose body is only break does nothing and is not counted.

    Before:

    // 11 clauses that each call a handler
    export class OrderProcessor {
      processOrder(status: string): void {
        switch (status) {
          case 'pending': this.reserveStock(); break;
          case 'processing': this.startPicking(); break;
          case 'shipped': this.notifyCarrier(); break;
          // ... 8 more clauses that call a handler
          default: break;
        }
      }
    }

    After (Factory Pattern):

    interface OrderStatusStrategy {
      execute(): void;
    }

    class PendingStrategy implements OrderStatusStrategy {
      execute(): void { /* ... */ }
    }

    class ProcessingStrategy implements OrderStatusStrategy {
      execute(): void { /* ... */ }
    }

    // ... more strategy classes

    class OrderStatusFactory {
      private strategies = new Map<string, OrderStatusStrategy>([
        ['pending', new PendingStrategy()],
        ['processing', new ProcessingStrategy()],
        // ... more strategies
      ]);

      createStrategy(status: string): OrderStatusStrategy {
        return this.strategies.get(status) ?? new DefaultStrategy();
      }
    }

    ISPViolationRule

    Rule ID: solid:isp-violation Severity: Warning

    Reports an interface that declares more than 5 methods, one warning at the interface. Methods are the interface's own method signatures counted by name (overloads once) plus properties whose type is a plain function (onSave: () => void, also optional or through a type alias). Callable types with properties of their own (signals such as title: Signal<string>), data properties, call and index signatures and members inherited through extends are not counted. Interfaces in declare global or declare module blocks and interfaces that merge with a declaration in a .d.ts file (a script-level interface Window) are skipped. Classes are not examined: how many interfaces a class implements is not reported.

    solid:import-direction-violation, solid:circular-dependency and solid:god-object-violation use the solid: prefix but belong to @angular-modernizer/plugin-architecture.

    OCPViolationRule

    Rule ID: solid:ocp-violation Severity: Warning

    Reports an if-else chain with more than 4 conditions (the if plus its else if links; a final plain else is not counted) when every condition compares the same discriminant with === or ==, also joined by || (kind === 'a' || kind === 'b'). The discriminant is a variable, parameter, property access chain such as this.state.kind or element access with a reference or literal key such as values[key]; two references match when they resolve to the same symbols and keys, so a.kind and b.kind are different discriminants. One warning per chain at its first if; the message names the enclosing function or method, the discriminant and the number of conditions and suggests a lookup map or polymorphism.

    Chains are checked in the whole file: methods, constructors, nested classes (each chain once) and functions outside classes. Switch statements are reported by solid:god-switch; parameter counts are not reported (no Open/Closed claim; ESLint max-params covers them).

    LSPViolationRule

    Rule ID: solid:lsp-violation Status: Deprecated, reports nothing (removed in 2.0)

    A class that misses a required member of an implemented interface or an abstract method of its base does not compile (TS2420, TS2515), so on code that builds these checks could only report members they did not see (inherited, optional, constructor parameter properties, arrow properties). An instanceof check alone (error instanceof HttpErrorResponse) shows no subtype that breaks its base's contract. The rule stays registered so configurations naming it load; ConfigLoader warns that rules['solid:lsp-violation'] has no effect.

    GodSwitchTransformRule

    Rule ID: solid:god-switch-transform Transformation Type: god-switch-transform

    Transforms God Switches into Factory Pattern implementations.

    Transformation steps:

    1. Detect switch statements exceeding the threshold
    2. Extract metadata: case logic, parameters, return types, mutations
    3. Generate strategy interface for polymorphic dispatch
    4. Generate one strategy class per case with extracted logic
    5. Generate factory class with strategy map and factory method
    6. Replace switch statement with factory call
    7. Update imports for generated code

    Before:

    export class PaymentProcessor {
      processPayment(method: string, amount: number): string {
        let result = '';
        switch (method) {
          case 'credit-card':
            result = `Processing credit card payment of ${amount}`;
            break;
          case 'debit-card':
            result = `Processing debit card payment of ${amount}`;
            break;
          case 'paypal':
            result = `Processing PayPal payment of ${amount}`;
            break;
          case 'bank-transfer':
            result = `Processing bank transfer of ${amount}`;
            break;
          case 'crypto':
            result = `Processing crypto payment of ${amount}`;
            break;
          // ... 10+ more cases
          default:
            result = 'Unknown payment method';
            break;
        }
        return result;
      }
    }

    After:

    interface MethodStrategy {
      execute(amount: number): string;
    }

    class CreditCardStrategy implements MethodStrategy {
      execute(amount: number): string {
        return `Processing credit card payment of ${amount}`;
      }
    }

    class DebitCardStrategy implements MethodStrategy {
      execute(amount: number): string {
        return `Processing debit card payment of ${amount}`;
      }
    }

    // ... more strategy classes

    class MethodFactory {
      private strategies = new Map<string, MethodStrategy>([
        ['credit-card', new CreditCardStrategy()],
        ['debit-card', new DebitCardStrategy()],
        ['paypal', new PaypalStrategy()],
        // ... more strategies
      ]);

      createStrategy(method: string): MethodStrategy {
        return this.strategies.get(method) ?? new DefaultStrategy();
      }
    }

    export class PaymentProcessor {
      private factory = new MethodFactory();

      processPayment(method: string, amount: number): string {
        const strategy = this.factory.createStrategy(method);
        return strategy.execute(amount);
      }
    }

    Configuration:

    interface GodSwitchTransformConfig {
      /**
       * Minimum case count to trigger transformation
       * Default: 10
       */
      minCaseCount?: number;

      /**
       * Generate strategy interface
       * Default: true
       */
      generateInterfaces?: boolean;

      /**
       * Generate factory class
       * Default: true
       */
      generateFactory?: boolean;

      /**
       * Strategy class naming pattern
       * Placeholders: {CaseValue}, {SwitchExpression}
       * Default: "{CaseValue}Strategy"
       */
      strategyNamingPattern?: string;

      /**
       * Factory class naming pattern
       * Default: "{SwitchExpression}Factory"
       */
      factoryNamingPattern?: string;
    }

    // Usage via MCP tool
    const result = await transformCode({
      filePath: 'src/app/payment-processor.ts',
      transformationType: 'god-switch-transform',
      config: {
        '@angular-modernizer/plugin-solid': {
          transformationType: 'god-switch-transform',
          godSwitch: {
            minCaseCount: 10,
            generateInterfaces: true,
            generateFactory: true,
            strategyNamingPattern: '{CaseValue}Strategy',
            factoryNamingPattern: '{SwitchExpression}Factory',
          },
        },
      },
    });

    Transformation guarantees:

    • Idempotent: safe to run multiple times, skips already-transformed switches
    • Atomic: all-or-nothing semantics with automatic rollback on failure
    • Mutation handling: preserves variable mutations across case boundaries
    • Fallthrough support: groups fallthrough cases into a single strategy
    • Type safety: generates TypeScript interfaces and typed factory methods

    ServiceDipViolationTransformRule

    Rule ID: solid:service-dip-violation-transform Transformation Type: service-dip-violation-transform

    Reads no findings (the analysis rule solid:service-dip-violation is deprecated and reports nothing): for each constructor parameter of an @Injectable class that injects a concrete @Injectable class, it adds an I{ClassName} interface (public method signatures) and a {CLASS_NAME}_TOKEN InjectionToken to the injected service file, changes the parameter type to the interface, adds @Inject(TOKEN) and the needed imports. Parameters that already have @Inject are skipped; an existing interface is not created again.

    Factory Pattern Comparison

    Aspect God Switch Factory Pattern
    Extensibility Modify switch for new cases Add new strategy class
    Testability Test entire switch Test strategies independently
    Maintainability Large, complex switch Small, focused classes
    OCP Compliance Violates OCP Follows OCP
    Code Reuse Duplicate logic Reusable strategies
    Type Safety String-based cases Interface-based polymorphism

    Usage Examples

    Basic SOLID Analysis

    import { Kernel, RealFileSystemAdapter } from '@angular-modernizer/core';
    import { SolidPlugin } from '@angular-modernizer/plugin-solid';

    const kernel = new Kernel({
      tsConfigPath: './tsconfig.json',
      fileSystem: new RealFileSystemAdapter(),
      plugins: [new SolidPlugin()],
    });

    await kernel.initialize();

    // Get SOLID analysis rules
    const plugin = kernel.getPlugin('@angular-modernizer/plugin-solid');
    const rules = plugin.getAnalysisRules();
    const dipRule = rules.find(
      (r) => r.id === 'solid:dip-violation-direct-instantiation',
    );

    // Analyze a file
    const project = kernel.getProject();
    const sourceFile = project.addSourceFileAtPath('src/app/user.component.ts');

    const context = ContextFactory.createAnalysisContext({
      sourceFile,
      project,
      api: createPublicApi(),
      config: {},
    });

    const results = await dipRule.analyze(context);

    console.log('DIP Violations found:', results.length);
    results.forEach((v) => {
      console.log(`- ${v.message} at line ${v.line}`);
    });

    Detection + Transformation (God Switch)

    // Get both analysis and transform rules
    const analysisRule = plugin
      .getAnalysisRules()
      .find((r) => r.id === 'solid:god-switch');
    const transformRule = plugin
      .getTransformRules()
      .find((r) => r.id === 'solid:god-switch-transform');

    // 1. Detect violations
    const analysisContext = ContextFactory.createAnalysisContext({
      sourceFile,
      project,
      api: createPublicApi(project),
      config: {},
    });

    const violations = await analysisRule.analyze(analysisContext);

    if (violations.length > 0) {
      console.log(`Found ${violations.length} God Switches, transforming...`);

      // 2. Transform violations
      const transformContext = ContextFactory.createTransformContext({
        sourceFile,
        project,
        api: createPublicApi(project),
        config: {
          '@angular-modernizer/plugin-solid': {
            transformationType: 'god-switch-transform',
            godSwitch: {
              minCaseCount: 10,
              generateInterfaces: true,
              generateFactory: true,
            },
          },
        },
      });

      const result = await transformRule.transform(transformContext);

      if (result.modified) {
        await sourceFile.save();
      }
    }

    Batch Analysis

    import { glob } from 'glob';

    const files = await glob('src/**/*.{ts,tsx}', {
      ignore: ['**/node_modules/**', '**/dist/**'],
    });

    const allViolations: Violation[] = [];

    for (const filePath of files) {
      const sourceFile = project.addSourceFileAtPath(filePath);
      const context = ContextFactory.createAnalysisContext({
        sourceFile,
        project,
        api: createPublicApi(),
      });

      for (const rule of rules) {
        const result = await rule.analyze(context);
        allViolations.push(...result.violations);
      }
    }

    // Group by severity
    const bySeverity = allViolations.reduce(
      (acc, v) => {
        acc[v.severity] = (acc[v.severity] || 0) + 1;
        return acc;
      },
      {} as Record<string, number>,
    );

    console.log('SOLID Analysis Summary:');
    console.log('High:', bySeverity.high || 0);
    console.log('Medium:', bySeverity.medium || 0);
    console.log('Low:', bySeverity.low || 0);

    SOLID Principle Reference

    Dependency Inversion Principle (DIP)

    High-level modules should not depend on low-level modules. Both should depend on abstractions.

    Reported by solid:dip-violation-direct-instantiation:

    • Direct instantiation of project @Injectable classes (new MyService())
    • Injector.get() lookups inside class members

    Best practices:

    • Use dependency injection
    • Program to interfaces, not implementations
    • Create abstractions for volatile dependencies

    Single Responsibility Principle (SRP)

    A class should have only one reason to change. One responsibility per class.

    Open/Closed Principle (OCP)

    Open for extension, closed for modification. Use polymorphism instead of conditionals.

    Liskov Substitution Principle (LSP)

    Subtypes must be substitutable for their base types. Inheritance should preserve behavior.

    Interface Segregation Principle (ISP)

    Clients should not be forced to depend on interfaces they don't use. Prefer small, focused interfaces.

    Contributing

    When adding new SOLID analysis rules:

    1. Focus on one principle - each rule should address one SOLID principle
    2. Use PublicApi tools - leverage existing analysis infrastructure
    3. Include auto-fixes when possible
    4. Write comprehensive tests covering various violation scenarios
    5. Document with before/after examples

    Adding a New SOLID Rule

    // 1. Implement the rule
    class MySolidRule implements AnalysisRule {
      readonly id = 'solid:my-solid-rule';
      readonly name = 'My SOLID Rule';
      readonly description = 'Detects violations of a specific SOLID principle';

      async analyze(context: AnalysisContext): Promise<AnalysisResult> {
        const { api, sourceFile } = context;
        const violations: Violation[] = [];

        // Use PublicApi for analysis
        // Detect violations and create Violation objects

        return {
          ruleId: this.id,
          violations,
          metadata: {
            totalViolations: violations.length,
          },
        };
      }
    }

    // 2. Add to plugin
    class SolidPlugin implements Plugin {
      getAnalysisRules(): AnalysisRule[] {
        return [
          new DIPViolationRule(),
          new MySolidRule(), // Add here
        ];
      }
    }
